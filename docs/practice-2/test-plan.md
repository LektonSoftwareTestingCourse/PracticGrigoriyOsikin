# Тестовый план СМП

## 1. Область и подход

План относится к релизной версии СМП в ветке практики 2. Система разворачивается через `docker compose` из текущего commit. Основной объект детального test-design — Authorization и Card Management; smoke и критический путь охватывают всю систему.

Последовательность работ:

1. Проверить требования, API-контракты и трассировку.
2. Подготовить `.env`, собрать и поднять PostgreSQL, RabbitMQ и 11 сервисов.
3. Выполнить health-check и дымовой чек-лист.
4. Создать независимые наборы карт и состояния usage.
5. Выполнить классы эквивалентности, граничные проверки и оба pairwise-набора.
6. Выполнить вручную добавленные критичные сочетания.
7. Проверить критический путь APPROVED и основные decline-сценарии через Gateway.
8. Зафиксировать результаты и дефекты, провести регрессию исправлений.

Тестовое окружение:

| Компонент | Конфигурация |
|---|---|
| ОС | Локальная Docker-совместимая среда |
| Оркестрация | `docker compose` из репозитория |
| Хранилище | PostgreSQL 16 Alpine, только синтетические данные |
| Брокер | RabbitMQ 3.13 Management |
| Входная точка | Gateway `localhost:8080` |
| Ядро | Card Management `:8081`, Switch `:8082`, Authorization `:8083` |
| Диагностика | container logs, health endpoint'ы, RabbitMQ Management UI |

Тестовые данные создаются API Card Management. Для непредставимых через публичный API состояний допускаются управляемые fixtures/stubs с обязательным описанием. Каждый денежный кейс получает отдельную карту либо полностью очищенное состояние.

## 2. Критерии входа и выхода

### Критерии входа

- ТЗ Authorization и Card Management доступны и не содержат неразрешённых блокирующих противоречий.
- Текущий commit зафиксирован, `.env` настроен, образы собираются.
- PostgreSQL и RabbitMQ имеют состояние healthy; миграции завершились успешно.
- Все обязательные сервисы отвечают на health-check.
- Зарегистрированы тестовые BIN, возможно создать/сгенерировать карты.
- Подготовлены модели и наборы pairwise, идентификаторы требований и ожидаемые результаты.

### Критерии приостановки

- Недоступен Gateway, Authorization, Card Management, PostgreSQL или RabbitMQ.
- Невозможно создать тестовую карту или восстановить исходное состояние balance/usage.
- Версия стенда изменилась во время прогона.
- Более 20% кейсов блокируются одной инфраструктурной причиной.

После устранения причины выполняются smoke и повтор затронутых кейсов.

### Критерии выхода

- Выполнены все строки обоих pairwise-наборов и все ручные критичные сочетания.
- Выполнены 100% P0/P1 и не менее 95% запланированных тестов в целом.
- Нет открытых Critical/Blocker; для открытых Major есть согласованное решение и оценка риска.
- Успешны smoke и критический путь `создание карты → авторизация → reserve → запись транзакции`.
- Для всех падений заведены воспроизводимые дефекты либо указана подтверждённая причина в тестовых данных/окружении.
- Результаты привязаны к commit и сохранены в Issue практики.

## 3. Ресурсы и расписание

| Этап | Результат | Оценка |
|---|---|---:|
| Анализ требований и архитектуры | Список требований, допущения, приоритеты | 2 ч |
| Тест-дизайн | Классы, границы, PICT-модели и ожидаемые результаты | 4 ч |
| Подготовка стенда и данных | Рабочая Compose-среда, тестовые карты | 1 ч |
| Прогон Authorization | Результаты AUTH и дефекты | 2 ч |
| Прогон Card Management | Результаты CMS и дефекты | 2 ч |
| Smoke и критический путь | Заполненные чек-листы | 1 ч |
| Регрессия и отчёт | Повторная проверка, готовый Issue | 2 ч |

Роли: студент отвечает за анализ, дизайн, прогон и отчёт; peer reviewer проверяет полноту и воспроизводимость; куратор выполняет приёмку. Нужны Git, Docker Compose, HTTP-клиент (`curl`/Postman), доступ к логам и RabbitMQ Management UI. PICT-модели и сгенерированные наборы хранятся в репозитории.

## 4. Риски

| Риск | Вероятность | Влияние | Мера снижения |
|---|:---:|:---:|---|
| Гонка между проверкой balance и reserve | Средняя | Критическое | Конкурентный тест, отдельный контроль отрицательного balance |
| Изменение usage одним кейсом влияет на следующий | Высокая | Высокое | Изолированные карты/fixtures, проверка предусловий |
| Eventual consistency ошибочно принимается за дефект | Высокая | Среднее | Polling с deadline, проверка очереди и логов |
| Случайный генератор делает тест нестабильным | Средняя | Среднее | Фиксированный seed/stub или проверка инвариантов вместо конкретного значения |
| Порты заняты или контейнеры используют старые образы | Средняя | Высокое | `docker compose ps`, фиксация commit/image, чистый перезапуск |
| Недоступность RabbitMQ маскирует дефекты сервисов | Средняя | Высокое | Разделять инфраструктурные и функциональные результаты |
| Timeout/retry увеличивают длительность теста | Средняя | Среднее | Управляемый stub и измеряемые границы ожидания |
| Требования и реализация расходятся по кодам ошибок | Высокая | Высокое | Трассировка к ТЗ, фиксация допущений, вопрос владельцу требований |
| Pairwise пропускает взаимодействие трёх и более факторов | Средняя | Высокое | Ручные P0-сочетания сверх 2-wise набора |
| Soft delete оставляет карту доступной операциям | Средняя | Высокое | Отдельная проверка GET/list/reserve после DELETE |

Главное допущение: ТЗ имеет приоритет над текущим поведением реализации. Неопределённый в ТЗ результат помечается как вопрос, а не автоматически как дефект.
