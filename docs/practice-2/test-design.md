# Тест-дизайн: Authorization + Card Management

## 0. Область тестирования и требования

Денежные значения передаются в копейках.

| ID | Требование                                                                                                                                                     |
|---|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| AUTH-01 | Карта должна быть получена из Card Management; неизвестный PAN отклоняется с `responseCode="14"`.                                                              |
| AUTH-02 | Статусы проверяются до остальных бизнес-проверок: `ACTIVE` допускается, `INACTIVE`/`BLOCKED` отклоняются с соответствующей причиной, `EXPIRED` - с кодом `54`. |
| AUTH-03 | Карта с `expiryDate` раньше текущего месяца отклоняется с кодом `54`; карта действительна до конца указанного месяца.                                          |
| AUTH-04 | `dailyUsage + amount <= dailyLimit`; при превышении - decline с кодом `61`.                                                                                    |
| AUTH-05 | Сумма дневных расходов текущего месяца плюс `amount <= monthlyLimit`; при превышении - decline с кодом `61`.                                                   |
| AUTH-06 | `amount <= availableBalance`; при превышении - decline с кодом `51`.                                                                                           |
| AUTH-07 | При прохождении проверок средства резервируются, возвращаются `APPROVED`, код `00`, уникальный 12-значный RRN и шестисимвольный `authCode` из `[A-Z0-9]`.      |
| AUTH-08 | Проверки выполняются строго в порядке: наличие карты -> статус -> срок -> дневной лимит -> месячный лимит -> баланс -> reserve.                                |
| AUTH-09 | При недоступности Card Management возвращаются `DECLINED`, код `05`, причина `ISSUER_TIMEOUT`.                                                                 |
| AUTH-10 | Bin Lookup вызывается с timeout 3/5 с и двумя попытками при 5xx; полученный `issuerId` используется для обогащения, при недоступности применяется fallback.    |
| CMS-01 | При создании генерируются валидный 16-значный PAN (BIN + 9 цифр + Luhn), expiry +3 года и статус `ACTIVE`.                                                     |
| CMS-02 | Получение карты по PAN возвращает карту либо 404.                                                                                                              |
| CMS-03 | Список карт имеет default `limit=50`, `offset=0`, пагинацию и фильтры `status`/`bin`.                                                                          |
| CMS-04 | `PATCH` частично обновляет только переданные статус, лимиты и баланс.                                                                                          |
| CMS-05 | `DELETE` выполняет soft delete; `DELETED` не выдаётся ни одиночным, ни списочным GET и не участвует в транзакциях.                                             |
| CMS-06 | Генератор равномерно распределяет карты по BIN; баланс 1 000 000–50 000 000, dailyLimit 5 000 000–30 000 000, monthlyLimit = dailyLimit × 30; статусы 95/3/2%. |
| CMS-07 | Reserve атомарно уменьшает `availableBalance` на положительную сумму и возвращает 200.                                                                         |

Базовая валидная карта для тестов авторизации: статус `ACTIVE`, неистёкший срок, `dailyLimit=10 000`, `monthlyLimit=30 000`, `availableBalance=20 000`, использовано сегодня `2 000`, использовано в текущем месяце `5 000`. Если в тесте не сказано иное, запрос содержит валидные обязательные поля и `amount=1 000`.

Техника: таблица решений. Условия проверяются сверху вниз. `-` означает, что условие не должно вычисляться из-за более раннего решения.

| Status ACTIVE |       -        |       -        | Нет: INACTIVE | Нет: BLOCKED | Нет: EXPIRED |      Да      |       Да       |       Да       |         Да         | Да |    Да    |

## 6. Баг-репорты

Баги локализованы по текущей реализации репозитория. Для интеграционных сценариев допускается управляемый stub Card Management, чтобы детерминированно воспроизводить ответы GET и reserve.

### BR-001: При одновременном превышении лимита и баланса возвращается причина недостатка средств

- **Требование:** AUTH-08, AUTH-04, AUTH-06.
- **Предусловия:** ACTIVE-карта с действующим сроком, dailyUsage=9 500, dailyLimit=10 000, availableBalance=100; amount=501.
- **Шаги воспроизведения:** отправить POST `/api/internal/authorize` для этой карты.
- **Ожидаемый результат:** дневной лимит проверяется раньше баланса; `DECLINED`, `responseCode="61"`.
- **Фактический результат:** возвращается `INSUFFICIENT_FUNDS`, `responseCode="51"`.
- **Локализация:** `AuthServiceImpl.authorize()` сравнивает amount с availableBalance до `checkAndUpdateLimits()`.
- **Severity / Priority:** Major / High.

### BR-002: Неуспешное резервирование расходует дневной и месячный лимиты

- **Требование:** AUTH-07, AUTH-09.
- **Предусловия:** ACTIVE-карта проходит все проверки; stub CMS отдаёт карту на GET, но отвечает 503 на reserve.
- **Шаги воспроизведения:** (1) выполнить authorize; (2) проверить `limit_usage`; (3) включить успешный reserve; (4) повторить тот же запрос.
- **Ожидаемый результат:** первый запрос отклонён без изменения `limit_usage`; повторный запрос оценивается с исходным остатком лимита.
- **Фактический результат:** `checkAndUpdateLimits()` выполняется до reserve, исключение reserve перехватывается и метод нормально возвращает decline, поэтому внешняя транзакция коммитит уже увеличенный usage.
- **Локализация:** `AuthServiceImpl.authorize()` - update лимитов перед `cardManagementClient.reserve()` и возврат из `catch` без rollback.
- **Severity / Priority:** Critical / Highest.

### BR-003: Срок карты проверяется относительно присланного времени транзакции, а не текущей даты

- **Требование:** AUTH-03.
- **Предусловия:** текущий месяц 09/2026; ACTIVE-карта имеет expiryDate=08/2026; остальные ограничения достаточны.
- **Шаги воспроизведения:** отправить authorize с `transmissionDateTime` из 07/2026.
- **Ожидаемый результат:** `DECLINED/54`, потому что на текущую дату карта истекла.
- **Фактический результат:** expiry-проверка проходит, так как 08/2026 сравнивается с датой запроса 07/2026.
- **Локализация:** `AuthServiceImpl.authorize()` вычисляет `transmissionDate` из `request.transmissionDateTime()` и сравнивает с `lastValidDay`.
- **Severity / Priority:** Major / High.

### BR-004: Мягко удалённая карта возвращается через GET и список карт

- **Требование:** CMS-05.
- **Предусловия:** существует ACTIVE-карта.
- **Шаги воспроизведения:** (1) DELETE `/api/cards/{pan}`; (2) GET `/api/cards/{pan}`; (3) GET `/api/cards` без status.
- **Ожидаемый результат:** шаг 2 - 404; в шаге 3 удалённая карта отсутствует.
- **Фактический результат:** `findByPan` не фильтрует `DELETED`, а построитель списка не добавляет условие `status <> DELETED`, поэтому карта доступна.
- **Локализация:** `CardRepositoryPersistenceAdapter.findByPan()` и `CardCriteriaBuilderJpaRepositoryImpl.createFiltersPredicate()`.
- **Severity / Priority:** Major / High.

### BR-005: Успешный ответ Bin Lookup не обогащает issuerId

- **Требование:** AUTH-10.
- **Предусловия:** запрос содержит fallback issuerId=`ISSUER_OLD`; Bin Lookup для PAN возвращает `ISSUER_NEW`.
- **Шаги воспроизведения:** отправить authorize и проследить используемый/возвращаемый issuerId.
- **Ожидаемый результат:** после успешного lookup используется `ISSUER_NEW`; fallback применяется только при ошибке lookup.
- **Фактический результат:** `ISSUER_NEW` только записывается в лог; объект запроса не заменяется через `withIssuerId`, поэтому продолжает использоваться `ISSUER_OLD`.
- **Локализация:** `AuthServiceImpl.authorize()`, вызов `binLookupClient.getIssuerId(...).ifPresentOrElse(...)`.
- **Severity / Priority:** Major / Medium.

### BR-006: Не проверяется уникальность authCode среди активных транзакций

- **Требование:** AUTH-07.
- **Предусловия:** генератор случайных значений принудительно/stub-ом возвращает уже активный `A1B2C3`.
- **Шаги воспроизведения:** (1) авторизовать первую транзакцию с authCode `A1B2C3`; (2) авторизовать вторую при том же результате генератора.
- **Ожидаемый результат:** обнаружение коллизии и повторная генерация до уникального кода.
- **Фактический результат:** обе транзакции получают одинаковый authCode; проверки хранилища активных транзакций нет.
- **Локализация:** `AuthServiceImpl.generateAuthCode()` генерирует строку и сразу возвращает её.
- **Severity / Priority:** Major / Medium.

### BR-007: GET списка карт по умолчанию запрашивает 10 элементов вместо 50

- **Требование:** CMS-03.
- **Предусловия:** в БД не менее 50 неудалённых карт.
- **Шаги воспроизведения:** выполнить GET `/api/cards` без query-параметров.
- **Ожидаемый результат:** ответ содержит до 50 карт при `offset=0`.
- **Фактический результат:** контроллер подставляет `limit=10`, поэтому сервисный default 50 никогда не используется.
- **Локализация:** `CardController.getCards()`: `@RequestParam(defaultValue = "10")`, при том что конфигурация задаёт `DEFAULT_PAGE_LIMIT=50`.
- **Severity / Priority:** Minor / Medium.

### BR-008: Недоступность Card Management возвращает код и причину, отличные от ТЗ

- **Требование:** AUTH-09.
- **Предусловия:** Card Management недоступен либо stub превышает read timeout на GET карты.
- **Шаги воспроизведения:** отправить валидный POST `/api/internal/authorize`.
- **Ожидаемый результат:** `DECLINED`, `responseCode="05"`, `declineReason="ISSUER_TIMEOUT"`.
- **Фактический результат:** формируется `SERVICE_UNAVAILABLE` с `responseCode="96"`.
- **Локализация:** `DeclineOutcome.SERVICE_UNAVAILABLE` использует `AuthorizationResponse.CODE_SERVICE_UNAVAILABLE`; в `AuthorizationResponse` эта константа равна `96`.
- **Severity / Priority:** Major / High.

## 7. Критерии завершения прогона

- Выполнены все 24 тест-кейса; для каждого сохранены дата, окружение, фактический результат и ссылка на дефект при падении.
- Decision table покрыта как минимум одним тестом на каждое правило R1–R11.
- Граничные проверки выполняются на изолированных картах/usage, чтобы предыдущий запрос не менял предусловия следующего.
- Для проверки уникальности RRN выполняется серия конкурентных успешных авторизаций; все значения имеют 12 цифр и не повторяются.
- Неуспешные сценарии не меняют balance и `limit_usage`.
