# API-тесты СМП — отчёт

## 1. Покрытие

Перечень сверен по [OpenAPI](../api/openapi.yaml), [текстовому контракту](../api-spec.md), [маршрутам Gateway](../../services/gateway/src/main/resources/application.yml) и контроллерам сервисов. Одна проверка ниже может выполнять несколько запросов, например создать карту, провести операцию и проверить новое состояние.

| Эндпоинт | Проверяемые статус-коды | Проверок или групп | Статус |
|---|---|---:|---|
| Gateway `GET /health` | 200 | 1 | Сводный статус и список зависимостей |
| Gateway `GET /{switch,logger,terminal,merchant,cards}-docs` | 200 | 5 | Версия OpenAPI и карта путей |
| `POST /api/cards` | 201, 400 | 6 + подготовка данных | PAN, имя владельца, пять негативных вариантов |
| `GET /api/cards` | 200, 400 | 5 | BIN, эмитент, статус, лимит и смещение |
| `GET /api/cards/{pan}` | 200 | 2 + проверки состояния | PAN, валюта, статус и баланс своей карты |
| `PATCH /api/cards/{pan}` | 200 | Подготовка данных | Явно заданный статус и баланс |
| `DELETE /api/cards/{pan}` | 204 | 2 | Пустое тело ответа и влияние на авторизацию |
| `POST /api/cards/generate` | 201 | 1 | Число и формат PAN сгенерированных карт |
| `POST /api/cards/bulk-update` | 200 | 1 | Изменяется указанная карта |
| `POST /api/cards/{pan}/reserve` | 200, 409 | 1 | Баланс после списания и конфликт повторного RRN |
| `POST /api/cards/{pan}/rollback` | 200 | 1 | Баланс после возврата |
| `POST /api/transactions` | 200, 400, 429 | 28 | Одобрение, валидация, сквозной поиск, отсутствие эффекта при отклонении входа, `Retry-After` |
| `GET /api/transactions/search` | 200, 400 | 32 + проверки эффектов | Фильтрация, пустая выдача, диапазон и пагинация |
| `GET /api/transactions/export` | 200 | 1 | CSV, имя файла, отбор и игнорирование смещения |
| `GET /api/dashboard/{stats,recent,charts}` | 200, 400 | 3 | Сохранённая транзакция, агрегация, границы `recent.limit` |
| `POST /api/simulator/terminal/run` | 200 | 1 | Один отправленный запрос и один результат |
| `POST /api/simulator/terminal/{start-continuous,stop}` | 200 | 1 | Запуск и остановка, пустые тела |
| `POST /api/simulator/merchant/run` | 200, 400 | 2 | Один результат и отказ при нулевом количестве |
| `POST /api/simulator/merchant/fee` | 404 | 1 | Сообщение и сервис для отсутствующей комиссии |
| `GET /api/simulator/merchants` | 200 напрямую, 404 через Gateway | 1 | Расхождение маршрутизации |
| Заявленные `POST /api/simulator/terminal/start`, `GET /api/simulator/terminal/status`, `GET /ws/transactions` через Gateway | 500 для terminal, 404 для WebSocket | 3 | Расхождения спецификации и маршрутов |
| Switch `POST /api/internal/route` | 200 | 2 | Неизвестный BIN и компенсация при сбое публикации |
| Authorization `POST /api/internal/authorize` | 200, 400, 403, 404, 422 | 9 + подготовка | Статус и пара «доменный код — причина» |
| Authorization `POST /api/internal/rollback` | 200, 404, 409 | 2 | Возврат, отсутствующий RRN, защита от двойного зачисления |
| Logger `POST /api/internal/log` | 200, 201, 400, 409 | 42 + подготовка | Валидация, повтор сообщения и контроль единственной записи |

Числа по строкам пересекаются. Напрямую вызываются участвующие в цепочке REST-контроллеры. У Card Management есть собственные маршруты `/api/bins`, у BIN Lookup — `/api/bin/{bin}`, у Notification — `/api/notifications`. Gateway их не публикует. BIN Lookup обогащает журнал Authorization и допускает сбой без изменения решения об авторизации. Полный прямой контракт этих сервисов, Actuator, Swagger UI и WebSocket-доставка остаются за границей набора.

|---|---|---|---|---|

| Дата операции позже срока карты | 54 | `CARD_EXPIRED` | Проверка даты при статусе `ACTIVE` | Передать дату на десять лет позже |

| Отсутствующая резервация | 14 | `TRANSACTION_NOT_FOUND` | Возврат по неизвестному RRN | Свежая карта и случайный RRN |
| Повтор возврата | 05 | `ALREADY_ROLLED_BACK` | Повтор того же возврата | Авторизовать, выполнить возврат дважды, сверить баланс |
| Ошибка публикации одобренной операции | 96 | `System error` | Switch выполняет компенсацию | Временно изменить только адрес порта AMQP у Switch, затем проверить баланс и выдачу |

Требуют отдельных управляемых отказов зависимости или гонки снятия средств: `SERVICE_UNAVAILABLE`, `DB_UNAVAILABLE`, `RESERVATION_FAILED`, `ROLLBACK_FAILED`, `UNKNOWN_REASON`, а также ветки блокировки через HTTP 402 и исчерпания средств между чтением карты и резервированием. Выше покрыты исходы, которые воспроизводятся через вход операции, состояние карты и предусмотренную проверку компенсации.

## 3. Валидация

| Вход | Правило | Классы и границы |
|---|---|---|
| Gateway, обязательные поля | Значение присутствует, строки непустые | Каждое обязательное поле удаляется отдельно, отдельная пустая строка |
| Gateway, MTI | `0100` | `0100` в сквозном тесте, `0400` отклоняется |
| Gateway, PAN | 16 цифр | 15, 16, 17 символов и буква при длине 16 |
| Gateway, валюта | Ровно 3 символа | 2, 3, 4 символа |
| Gateway, MCC | Ровно 4 цифры | 3, 4, 5 символов и 4 буквы |
| Gateway, сумма | Строго положительная | Отрицательная, ноль и положительная |
| Gateway, тело | Корректный JSON и ненулевой объект | Некорректный JSON, JSON `null` и корректный объект |
| Logger, обязательные поля | UUID, даты, статус, сумма и обязательные строки | Каждое из 14 полей отсутствует в отдельном запросе |
| Logger, длины и форматы | Размеры и регулярные выражения DTO | 23 неприемлемых значения, включая короткие и длинные STAN, PAN, коды валют и обработки |
| Logger, числа | Положительная сумма, неотрицательная комиссия и длительность | 4 негативных значения |
| Параметры поиска | `limit` 1–500, `offset` от 0, даты и enum разбираются | 0, 1, 500, 501, −1, нечисловой лимит, неизвестный статус, невозможная дата, обратный диапазон |
| Создание карты | BIN, имя, длина кода валюты, неотрицательные лимиты | Короткий BIN и код валюты, строчное имя, отрицательные дневной и месячный лимиты |
| Параметры списка карт | Положительный лимит, неотрицательный offset, BIN и issuerId | 0 для лимита, −1 для offset, пятизначный BIN, строчные буквы в issuerId |
| Dashboard и Merchant | `recent.limit` 1–500, `count ≥ 1` | 0, 1, 501 для `recent.limit`, 0 и 1 для `count` |

Тела ошибок Gateway проверяются по точному тексту, коду и `serviceName`. Для Logger проверяются сервис, класс ошибки и имя поля. Матрица пока не перебирает все правила для Create/Patch/Bulk/Generate, форматы внутренних DTO Authorization, параметры симуляторов, CSV и графиков.

## 4. Расхождения контракта и реализации

| Декларировано | Наблюдается | Источник | Классификация |
|---|---|---|---|
| В одобрении `mti=0110` | Ответ успешной авторизации содержит `0100` | Пример в `api-spec.md`, `AuthorizationResponse.approved` | Дефект контракта ISO 8583. Клиент может перепутать запрос и ответ |
| `POST /api/simulator/terminal/start` возвращает 202, `GET .../status` возвращает состояние | Оба пути возвращают 500 из общего обработчика исключений Terminal Simulator. Работают `POST .../start-continuous` и `POST .../stop` с 200 и пустым телом | OpenAPI, `TerminalSimulatorController` | Дефект совместимости для сгенерированных клиентов |
| Каталог мерчантов доступен в публичном API | Контроллер отвечает 200 напрямую, через Gateway тот же путь даёт 404 | OpenAPI, маршрут `/api/simulator/merchant/**` | Дефект маршрутизации |
| WebSocket-путь указан рядом с REST-эндпоинтами | Gateway отвечает 404 на HTTP-запрос к пути. WebSocket объявлен в Logger | OpenAPI, `WebSocketConfig`, маршруты Gateway | Ограничение публичного доступа. WebSocket-обмен вне области REST |
| `retryAfterMs` объявлен целым числом | Logger и Merchant формируют строку из поля общего DTO. Rate limiter формирует собственное числовое поле | OpenAPI, `ErrorResponse`, `TransactionRateLimitFilter` | Дефект согласованности типов, вывод по коду |
| Switch вызывает Logger по внутреннему REST API | Обычный маршрут публикует в RabbitMQ, внутренний HTTP-эндпоинт Logger принимает запрос отдельно | `api-spec.md`, `RouteService`, `LoggerClient`, `InternalTransactionController` | Устаревшее описание реализации. Сквозная проверка использует публичные HTTP-запросы |

Для MTI и обещанных публичных маршрутов ожидаемое клиентом поведение задаёт спецификация. Набор воспроизводит фактические ответы стенда, чтобы известные дефекты оставались видимыми при регрессии. Для внутреннего способа доставки актуален код Switch, поскольку он определяет работу запущенного стека.

## 5. Обоснование достаточности

- PAN новой карты выдаёт Card Management, STAN формируется для каждой операции, UUID записей Logger генерируется заново. В сценарии повтора идентификаторы намеренно переиспользуются. Карты, статусы и резервации готовятся через HTTP.
- В таблице поиска 16 строк обеспечивают попарное покрытие присутствия и отсутствия девяти опциональных параметров. PAN фиксирует выборку на собственной записи. Дополнительные тесты меняют каждый фильтр независимо, проверяют исключение записи, обратный диапазон и предельное смещение.
- Для Logger проверяются три разных состояния одного ID: первое сохранение, повтор тела, повтор с изменённой суммой. Последующий HTTP-поиск проверяет исходную сумму и единственность записи.
- Ожидание сквозной записи ограничено 15 секундами с опросом каждые 250 мс. Для отсутствия эффекта проверка должна оставаться верной две секунды подряд с тем же интервалом. Сценарий сбоя использует отдельную фазу стенда с неверным AMQP-портом Switch. Проверяются доменный ответ, баланс и отсутствие записи.
- Покрытие ограничено проверенными классами и ветками из разделов 1–3. Для полного соответствия критериям задания остаются систематические статусы недоступности, позитивный поиск комиссии и негативные варианты ряда эндпоинтов. Внутренние состояния PostgreSQL и RabbitMQ по API этих компонентов не проверяются.

## 6. Доказательства работоспособности проверок

Мутационный прогон выполнен в отдельной копии исходников и на отдельном Compose-проекте. Surefire выполнил 8 случаев и зафиксировал 4 ожидаемых падения без ошибок исполнения.

| Тест | Внесённое изменение | Результат |
|---|---|---|
| `sameIdAndPayloadAreIdempotentAndDifferentPayloadConflicts` | В `TransactionService.store` отключены поиск существующего ID и обработка конфликта при сохранении | Повтор вернул 201 при ожидаемых 200 |
| `approvedPaymentIsFindableByPanAndStan` | Ожидание доменного кода изменено с 00 на 99 | Получен 00 при ожидаемом 99 |
| `authorizationDeclinesBasedOnIndependentCardConditions` | Для блокировки ожидается `CARD_INACTIVE` | Получен `CARD_BLOCKED` при совпадающем коде 05 |
| `generateCreatesRequestedNumberOfCards` | Для запроса одной карты ожидаются две | Поле `generated` равно 1 при ожидаемых 2 |

## 7. Порядок запуска

Из корня репозитория с Java 21, Maven и Compose v2.24.4+:

```bash
scripts/api-tests.sh
```

Скрипт поднимает изолированный стек с параметрами из `.env.example`, ждёт готовности и определяет выделенные Docker локальные порты. После обычного Maven `verify` запускаются компенсационный сценарий и проверка `429` с ёмкостью лимитера в один запрос без пополнения. В конце удаляются контейнеры и том только этого прогона. Для одного обычного теста можно передать Maven-фильтр, например `scripts/api-tests.sh -Dtest=TransactionLoggerTest`.

Пайплайн [Practice 5 API contracts](../../.github/workflows/practice-5-api.yml) запускается автоматически на push веток `practice-5*` и сохраняет отчёты Surefire как артефакт. Его также можно запустить через `workflow_dispatch`.
